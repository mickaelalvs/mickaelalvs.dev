<br />

A devtool makes implicit state visible. Why is this query stale? Which config applies to this file? How did the bundler transform this module? You stop guessing and look.

Modern tools rarely ship without one anymore. TanStack Query and Router, Redux, React Hook Form, Vue and Nuxt DevTools, Vite DevTools, ESLint Config Inspector, the Oxc Inspector... And those are only the ones someone else wrote. Building your own isn't an exotic idea either. [Kent C. Dodds was already writing about it years ago](https://kentcdodds.com/blog/make-your-own-dev-tools), with feature toggles, form autofill and backend switching, all hand-rolled.

So you end up with two families. The devtools your libraries ship, and the ones your team builds for its own product. Neither knows the other exists. A browser extension here, a floating button injected into your app there, a URL logged in the terminal, a homemade console command for the rest.

Taken one by one, each of these tools improves DX. Stacked with no coordination, they do the opposite. You can't see your screen anymore, and you spend more time closing panels than debugging.

This article is about putting all of them in one place, the devtools you install and the ones you build.

## 🧰 What a team actually needs

<br />

I work on a Platform Frontend team. We look after a large monorepo with several apps, shared packages, a design system, and **dozens of developers** shipping in it every day.

That monorepo keeps gaining tools. Every migration brings one in, and each new data-fetching library, router or bundler ships its own devtools. Good news, until you count them.

When we bring in a tool or a feature, we want it to land with the best DX we can give it, not with a README page explaining which snippet to paste in the console. At this scale, every bit of friction gets multiplied by dozens of developers and several apps.

Official devtools cover the libraries. They don't cover your product. We also wanted panels for an analytics event log, feature flipping shortcuts, the current layout, and our own state. Until now, we built that plumbing by hand, for every new need, in every app.

So the requirements were short:

- one shared shell for the devtools we install and the ones we build, instead of five floating panels
- custom panels written as regular components, in each team's framework
- a way to move data across tabs and out to the dev server
- zero cost in production

## 🔄 The one I tested: TanStack Devtools

<br />

[TanStack Devtools](https://tanstack.com/devtools/latest) goes after exactly this. Its docs sum it up in one line: _"Build the inspector, not another debugging shell."_

It's a framework-agnostic shell that any library or team can plug a panel into. Official devtools like Query, Router or Form are plugins, and so are yours. Under the hood, there are three layers:

- **framework adapters** (`@tanstack/react-devtools`, `@tanstack/vue-devtools`...) that expose the API in your framework
- **the core shell** (`@tanstack/devtools`), written in Solid.js, whatever your app uses, which handles plugins, tabs, settings and shortcuts
- **the event system** (`@tanstack/devtools-event-client`), a typed pub/sub connecting your app to the Vite server over WebSocket or SSE

The _plugin workspace_ tiles several plugins into resizable panels, mini-IDE style. Query, Router and your own panels share the screen instead of fighting over it.

It supports React, Vue, Solid, Svelte, Angular, Preact and vanilla JS. A plugin is a component in your framework, so a React team ships a React component and a Vue team a Vue one, in the same shell.

### Plugging in your own panel

A custom plugin is a component you pass to the `plugins` prop:

```tsx
<TanStackDevtools
  plugins={[
    {
      name: 'Feature Flipping',
      render: <FeatureFlippingPanel />,
    },
  ]}
/>
```

No class to extend. `FeatureFlippingPanel` is a plain React component, so the only question left is how it talks to your app. There are two ways.

### Reading from an existing store

If a store already runs in your app (Redux, Zustand, Jotai...) and the devtools sit inside its `<Provider>`, the panel subscribes like any other consumer. That's the easy path. It stops at the tab, though. An analytics log across two tabs, or debugging a Backend for Frontend (BFF), needs something else.

### Going through the event bus

The event bus crosses tabs and reaches the dev server. It's also the only contract a published plugin can rely on, since the plugin can't know the shape of your store. The cost is an `emit()` at every point you want to see.

```ts
import {EventClient} from '@tanstack/devtools-event-client';

type MyEvents = {
  'feature-flag-toggle': {flag: string; enabled: boolean};
};

class TeamEventClient extends EventClient<MyEvents> {
  constructor() {
    super({pluginId: 'team-devtools'});
  }
}

export const teamEventClient = new TeamEventClient();
```

The panel emits when you toggle a flag, and a small module on the app side listens and overrides the real value:

```ts
// in the panel
teamEventClient.emit('feature-flag-toggle', {flag: 'new-checkout', enabled: true});

// in the app
const overrides = {};

teamEventClient.on('feature-flag-toggle', (e) => {
  overrides[e.payload.flag] = e.payload.enabled;
});

function isEnabled(flag) {
  return overrides[flag] ?? realValue(flag);
}
```

Each feature team now defines its events and its component, and that's it. The shell handles positioning, shortcuts and persistence for everyone. To keep panels out of the production bundle, `@tanstack/devtools-utils` has `createReactPlugin`-style factories that return a no-op twin.

### One of my favorite features: go to source

The Vite plugin (`@tanstack/devtools-vite`) ships [a list of built-in features](https://tanstack.com/devtools/latest/docs/vite-plugin#features). This is the one I'd miss most.

At build time, it parses your JSX/TSX with `oxc-parser` and adds a `data-tsd-source="file:line:column"` attribute to every element. In dev, you hold a shortcut, hover anything on the page, and click. Your editor opens at the right line through [`launch-editor`](https://github.com/vitejs/launch-editor), the library Vite itself uses, with no configuration.

The click travels over the event bus to the Vite server, which calls `launch-editor`. Browser to Node, the exact trip a shared store can't make.

I loved it the moment I tried it. On a big design system, finding the file behind a piece of UI turns into a treasure hunt. For someone new to the codebase, no more grepping a class name to find the component behind a visual bug. You click, you're in the file.

Browser `console.log` calls get the same treatment, with a clickable `file:line`, and logs flow both ways between browser and terminal. There's also a [plugin marketplace](https://tanstack.com/devtools/latest/docs/third-party-plugins), with an `axe-core` accessibility overlay and a TanStack AI plugin, and nothing stops a platform team from publishing its own internal plugins.

## 🌐 What if we went even more generic? Meet Devframe

<br />

TanStack Devtools fixes the problem inside your app's page. The same fragmentation exists one level down, in the tools themselves. Every devtool rebuilds its own RPC, state sync and web UI, wired to one framework's dev server, and the next framework rebuilds it slightly differently.

[Devframe](https://devfra.me/) tackles that. Led by [Anthony Fu](https://github.com/antfu) and born out of the work on Vite DevTools at Vercel, it hit **v1.0** in September 2026. It's a framework for building devtools, the way Nuxt or Next.js is a framework for building web apps. The docs also call it _"`unplugin` for devtools"_. You define a tool once, and the same definition runs almost anywhere.

- **One definition, many targets.** A dock in Vite or Nuxt DevTools, a route in Next.js, SvelteKit or Hono, a standalone CLI, or a static report in your CI.
- **Any UI framework.** The tool's UI is a regular SPA, in Vue, React, Svelte or Solid.
- **Typed RPC and shared state** between Node and the browser, over WebSocket or SSE.
- **Agents built in.** Flag an RPC function and it becomes an MCP tool your coding agent can call.
- **A hub** that gathers every devframe behind one entry point, instead of a terminal full of URLs.

Reading the docs felt like reading our requirements list, pushed further. One place for the tools you install and the ones you build, panels in each team's framework, data crossing the browser boundary. It's what TanStack Devtools pushes for, one level lower and without being tied to your app's page.

Then there's the part TanStack Devtools doesn't touch. Devframe is built for humans and for agents. The same function sits behind the button in your panel and behind an MCP tool, so our feature flag toggle becomes something Claude Code can flip itself while it works on the new checkout. The announcement even pictures asking an agent for a throwaway devframe, built to answer one question and then dropped.

And it's already in use. The post splits devtools into layers, and each one has real examples:

- **General capabilities**, built once for every host. Accessibility, terminals, a data inspector, MCP.
- **Build tools.** Vitest, Rolldown and Oxc, all in the new Vite DevTools dock.
- **Framework-specific panels.** Nuxt DevTools v4 builds on Devframe, and Vue DevTools is migrating to it.
- **Ecosystem tools.** ESLint Config Inspector, UnoCSS Inspector, Node Modules Inspector.

So the two don't compete. TanStack Devtools is a product, a shell that lives in your app's page. Devframe is the framework you'd build that kind of product with. They overlap on the plumbing: gathering several tools in one place, and talking to the server. That's the part TanStack could hand over to Devframe while keeping its plugin API. ## 🚀 What actually changes

<br />

This piece of DX used to be built by hand, or not at all. We lived with the friction and the longer onboarding and called it the price to pay. TanStack Devtools makes it cheap inside your app. Devframe takes the same idea across every host, and hands your tools to your agent too.

The Devframe post says a good tool should be built once, travel further, and get better as more people contribute. That holds for the ecosystem, and it holds for a monorepo with dozens of developers. Build it once, give it to every team, and close those five floating panels for good.

A lack of DX never shows, until the day you fix it. Your teams deserve devtools.
